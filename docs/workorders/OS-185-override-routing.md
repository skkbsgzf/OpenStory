## 目标

`overrides` 注册表在运行时真正起作用：同能力多供给时按优先级路由（本机覆盖内置＞装载顺序）；覆盖者被停用或卸载后**自动回退**到被覆盖者或更低优先的供给者。路由表从「进程周期内静态」演进为「重建＝重新校验后再切换」。

## 任务

1. **运行时路由**：`resolve(capabilityId)` 按 `overrides` 关系与优先级选供给者；句柄是薄代理（OS-175 已提供），本单让代理在路由表重建后指向新供给者，消费方无感。
2. **回退链**：覆盖者停用／卸载 → 触发路由表重建（重跑三项检查）→ 切换到下一优先供给者；若没有可用供给者，按「消费者降级」语义处理并列出受影响方。
3. **成环拒绝**：两个插件互相覆盖 → `CAPABILITY_CONFLICT`，两份都不受理（保留被覆盖前的路由）。
4. **协议更新**：`docs/protocol/module-manifest-2.md` 的「路由表冻结」一节改为「重建规则」；写明热更新期间进行中的调用如何收尾（建议：进行中的调用用旧句柄跑完，新调用走新路由）。
5. **测试**：覆盖生效→停用覆盖者→自动回退（消费方拿到的结果随之变化）；优先级（本机＞内置）；成环拒绝；重建期间并发调用不混用两个供给者。

## 不做

- 不动迁移器（OS-186）；不改任何现有能力的实现。
- 不开放第三方插件的装载（装载源仍是仓库 `src/modules/` 与本机套件货架）。

## 验收

- 全量测试与验收门禁全绿。
- **回退演练**：测试夹具里用覆盖者替换某能力→消费方读到覆盖者的输出→停用覆盖者→不重启进程，消费方读回原供给者的输出；全程输出贴报告。
