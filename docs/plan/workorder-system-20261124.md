## 4. 工单规范

- 一单文件：`docs/workorders/OS-<编号>-<短名>.md`；看板 `docs/workorders/BOARD.md`。
- 固定段落：头部元数据表（批次／依赖／允许改动范围／风险／状态）→ 目标 → 动工前必读 → 任务 → 不做 → 验收 → 纪律 → 施工回报（编排器自动归档）→ 验收记录（主 agent 填）。
- **允许改动范围**是硬约束：越界的改动一律不提交，触发返工。
- 状态：待派 → 施工中 → 检查中 → 待验收 → 已验收；异常走 返工 / 停线 / 挂账。返工另立修复工单，不原地改已验收的提交。
- 编号顺延，不重用；与路线条目的对应关系写在元数据里。
- **段内修复不占新号**：验收或复核发现的问题，用「上一张已派工单号＋字母」立修复单（如 OS-150a），后续计划的编号不顺延。

## 5. 派发流水线

```
node .zcode/os-batch-runner.mjs --plan <plan.json> --status <status.json> --model deepseek-v4.1-flash --rounds 2
```

每张工单依次经过：

1. **开工前**：工作树干净、编排器自身无未提交改动、全量测试基线绿；否则不开工。
2. **施工**：`codebuddy -p --model deepseek-v4.1-flash`，工单经 stdin 喂入，施工方不碰 git。
3. **范围检查**：改动文件必须落在工单的允许范围内；`package.json` 的版本与依赖不许动；`core/**`、`vendor/**` 除非工单写明否则不许动；探针与临时文件不许留下。
4. **五道门禁**：全量测试、验收门禁、水浒 10 项、新建 13 项、vendor 漂移（门禁前自检 daemon，掉了就拉起并写明）。工单点名的「红线测试」单独跑并逐个报告。
5. **不过则返工**：带失败输出与越界清单重派，最多两轮。
6. **提交**：编排器提交（只含范围内的文件），施工回报自动归档进工单文件。
7. **验收**：主 agent 浏览器实测（只用临时夹具库）→ 需要时派独立复核（CLI 只读）→ 结论写进看板。

**停线**（等主 agent，不自动继续）：两轮后门禁仍红；两轮后仍有越界改动；CLI 超时（3 小时）；施工方上报规格矛盾。

## 6. 复核与验收

- 段末独立复核：每段做完派一次只读复核，逐条核本段各单的验收点；发现的问题另立修复工单，修完再核一次。
- 高危单（OS-156、OS-157、OS-163、OS-164）单独各复核一次；段 B 的设计稿（OS-151）由主 agent 验、作者过目命名。
- 浏览器验收清单（每段末）：进库 → 正文（含拨模块开关后切回）→ 世界书 → 故事源 → 剧本 → 扮演 → 产物 → 习惯 → 设置（模块组、运行时列表）→ 库切换面板；全程临时夹具库，作者真库与本机真实院子不动。

## 7. 红线

两批路线的红线继续有效（fact-first 不稀释、写通道收敛、能力白名单前置、核心插件保底、零构建、每批界面可见＋测试全绿＋文档同批；金样不动、旧院不删、旧库不迁移、每步独立提交）。本体系的调整与补充：

- **「vendor 边界不动」自作者 2026-11-24 裁定起不再适用于 `core/**` 与 `vendor/**`**——两者全部转自有。但它保护的东西换了个护法：**磁盘格式不动**（金样、旧库目录、互认的锚），代码怎么改名、怎么重排都行。
- **出处声明随代码走**：转自有时把 `core/VENDORED.md` 记载的出处（Pinax-next `70a4f44`）改写进 README 致谢段与文件头注释，`PUBLISHING.md` 同步口径；不随 vendor 身份一起删。
- **对外契约不随内部改名而变**：MCP 工具名、端点路径、API／MCP 的错误码字符串（要改另立工单并带兼容别名）。
- **测试与施工永不碰真实数据**：`%LOCALAPPDATA%\PinaxNext\`（真实院子）与 `D:\Projects\`（作者真库）；迁移类逻辑只在临时目录上验证。
- **高危单开工前主 agent 先备份现场**。
